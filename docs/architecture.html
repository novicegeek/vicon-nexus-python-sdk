Architecture

Knowing the SDK's four layers explains most of the "why did this call do nothing?" and "why this error?" questions.

Call chain

your code
  │
  ▼
L1  facade           viconnexusapi.ViconNexus.ViconNexus
    marshals Python ↔ C++ values: list ↔ vector, str ↔ SafeString,
    dict ↔ map; prints failures (GenerateErrors); owns the method
    names and docstrings you read in this reference
  │  self.Client = nexusclient.ViconNexusClient()
  ▼

    depends on boost_python27 / boost_system / boost_thread DLLs
  │  in-process IPC
  ▼
L4  transport        ViconSDKClientCPP.dll / NexusSDKClientCPP.dll
    connects to the running Nexus process and exchanges commands
  │
  ▼

Which binding gets loaded: Python 2 or 3

The top of ViconNexus.py picks the low-level module by interpreter version, which is transparent to callers: 

if sys.version_info > (3, 0):
    from . import NexusClient3 as nexusclient     # binds _NexusClient3.pyd
    ...
else:
    from . import NexusClient as nexusclient      # binds _NexusClient.pyd
    ...

Both bindings expose the same method names, so application code needs no branching. Strings are the one real difference: in Python 2 a str is bytes, which is why the facade funnels every returned string through _get_safe_string_value() and decode('utf-8') — what you receive is always str. Conversely, every argument is .encode('utf-8')-ed before it crosses the boundary.

Return values: the Output_Result family

Every low-level command returns an Output_* object. They all derive from Output_Result, so all of them have:

MemberMeaning
Error()bool — did the command fail?
ResultString()SafeString — why it failed

Each type then adds its own data members: Output_GetTrajectory carries X/Y/Z/E, Output_GetSubjectNames carries Names/Models/Active. The facade's job is to translate those members into Python lists and tuples.

One GetTrajectory call, end to end

# your code
x, y, z, e = vicon.GetTrajectory('Colin', 'C7')

# L1: encode the strings → call L2 → check for errors → expand 4 vectors into lists
def GetTrajectory(self, subject, marker):
    data = self.Client.GetTrajectory(subject.encode('utf-8'),
                                     marker.encode('utf-8'))
    if data.Error() and self.GenerateErrors:
        print(ViconNexus._get_safe_string_value(data.ResultString), file=sys.stderr)
    x, y, z, e = list(data.X), list(data.Y), list(data.Z), list(data.E)
    return x, y, z, e

# L2: SWIG forwards to _NexusClient3
def GetTrajectory(self, i_rSubjectName, i_rMarkerName):
    return _NexusClient3.ViconNexusClient_GetTrajectory(
        self, i_rSubjectName, i_rMarkerName)
Consequence On failure data.X and friends are still empty containers, so the method returns four empty lists instead of raising. "No data" therefore usually shows up as a length of 0, not as an exception.

Packaging

setup.py reads the version from the sibling VERSION file, collects packages with find_packages(), and relies on include_package_data=True plus MANIFEST.in to carry the .pyd and .dll files along. In other words: a wheel built from this directory already contains the binaries, so end users never have to copy DLLs by hand.

Threads and concurrency

  • Client and Nexus speak a command/response protocol: only one command may be in flight. Concurrent calls from several threads need your own lock.
  • Methods that take a timeout (RunPipeline, OpenTrial, …) only give up waiting client-side; the host may still be working.
  • Long loops inside a Nexus-hosted script block the UI — drive them from an external process instead.
